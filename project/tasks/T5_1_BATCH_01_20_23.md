# T5.1 · Batch 01 · reconciliación canónica 20–23

Issue: #2

## Objetivo

Reconciliar el primer lote de contenido principal de la fase `20_23` sin aliases silenciosos. Este lote cubre los seis IDs canónicos ausentes detectados por la auditoría reproducible.

## Hallazgo estructural

El inventario canónico y el motor tienen el mismo número total de principales en esta fase, pero no la misma identidad. El motor usa además una plantilla genérica (`make(row)`) para muchas escenas: cuatro opciones reutilizadas por familia, texto visible genérico e incertidumbre genérica. Esa estructura sirve como adaptación técnica, pero no acredita fidelidad semántica.

Por tanto T5.1 **no debe resolverse renombrando IDs**. La escena canónica tiene que conservar su situación, información imperfecta, dilema y memoria propia.

## Arquitectura de implementación recomendada

La fase 18–20 ya demuestra el patrón adecuado mediante `canonical-events.ts`: eventos `ambiguousEvent(...)` explícitos con cuerpo, visible, incertidumbre, elecciones, resultados y seeds propios.

Para este lote, preferir uno de estos dos enfoques, por orden:

1. crear `src/content/events/20_23/canonical-events.ts` para las seis escenas y componer el catálogo de principales de forma explícita; o
2. convertir únicamente estas seis escenas a definiciones explícitas dentro de `principal-events.ts` si separar el archivo complica el catálogo.

No duplicar IDs y no parchear `dist/`, PlayCanvas o Android manualmente.

## Compatibilidad de guardado

`GameSession.resume()` compara el SHA-256 del `JSON.stringify(events)` con `snapshot.contentIdentity` y lanza `CONTENT_CHANGED` cuando cambia el catálogo. Por tanto, cualquier modificación de contenido altera la identidad y debe tener una decisión explícita:

- o se añade una migración compatible para saves anteriores;
- o se documenta formalmente que el cambio de T5.1 requiere migración antes de reanudar esas partidas.

No debilitar la comprobación `contentIdentity` para hacer pasar el lote.

## Criterios de aceptación

1. Los seis IDs canónicos existen exactamente una vez entre los principales activos.
2. Trigger, visible, incertidumbre, opciones y seeds son específicos del canon, no la plantilla genérica.
3. `canonStatus` solo será `verified` si la implementación queda comparada explícitamente con `principal-traceability.json`; en caso contrario mantener `technical_adaptation` hasta cerrar revisión.
4. Los seis IDs técnicos extra reciben una decisión documentada: retirar, migrar o conservar fuera del conjunto canónico.
5. No se crean aliases automáticos.
6. El auditor T5.1 reduce los seis unresolved por evidencia real, no por equivalencia nominal.
7. No se rompe separación RNG ni la regla de lecturas sin efectos.
8. La estrategia de saves queda probada/documentada.
9. Ejecutar como mínimo:

```bash
npm run build
npm run validate
npm run test:session
npm run test:saves
npm run audit:t51
npm run test:t51
```

Añadir pruebas dirigidas para los seis eventos y para cualquier migración de IDs/contenido.
